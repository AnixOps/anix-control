# Control 首批运维手册

本手册说明机器监控插件和运维工作台。当前验收证据见 [首批记录](P4_EXECUTION_STATUS.md)，后续网络功能继续按 [路线图](../ROADMAP.md) 验收。

## 启动与入口

使用同一 GitHub Actions release 的后端和前端。开发启动入口是 `go run ./cmd/server -config config/config.yaml`；生产使用已发布 `anix-control -config <受控配置路径>`。配置模板在 `config/config.yaml.example`，开发时复制后设置独立数据库。不要用生产数据库运行测试。

后端主进程在现有 Kernel schema 初始化中创建独立 `ops_*` 运维表及 `v3_maintenance_*` 变更表；这属于 schema 写入，上线须提前在备份副本审查和演练。当前没有单独的生产运维 schema 迁移批准执行器。后台任务启动立即补跑，之后每 30 秒消费、升级、通知和保留清理；SIGTERM 取消任务并等待退出。日志写入现有标准输出/服务管理器日志；失败只输出固定类别，待处理数据保留在数据库。

登录后进入 `/maintenance`，管理端和用户工作区都有入口。客户售后仍使用原工单页面；运维不向客户 `v2_ticket` 写入。普通用户不能读取运维数据。负责人或指定技术员由服务端判定，不依赖前端按钮隐藏。

## 负责人、技术员与渠道

首次由管理员在“运维设置”指定负责人、技术员用户 ID 和每个人的邮件/Telegram chat ID。没有技术员时负责人接收普通通知。保存设置后分别发送邮件和 Telegram 验证码、输入收到的验证码，两个渠道都确认成功才可正式启用。负责人/渠道更换会撤销对应验证；修订号阻止并发覆盖。页面不会返回验证码或服务端凭据。

部署平台注入以下环境变量（仓库不提供实际值）：

| 名称 | 用途 |
|---|---|
| `ANIXOPS_MAINTENANCE_SMTP_HOST` | SMTP 主机 |
| `ANIXOPS_MAINTENANCE_SMTP_PORT` | STARTTLS 端口，默认 587 |
| `ANIXOPS_MAINTENANCE_SMTP_FROM` | 发件地址 |
| `ANIXOPS_MAINTENANCE_SMTP_USERNAME` / `ANIXOPS_MAINTENANCE_SMTP_PASSWORD` | SMTP 认证 |
| `ANIXOPS_MAINTENANCE_TELEGRAM_TOKEN` | Telegram Bot token |

邮件必须支持 STARTTLS（TLS 1.2+），发送前校验服务器证书；当前不支持隐式 TLS 465。Telegram 调用官方 HTTPS API，禁止跟随重定向。每次发送最多 15 秒，两个渠道独立失败重试（30 秒逐级至 30 分钟）。不要在开发验收时配置真实接收人；自动测试使用注入的发送器。

通知领取使用数据库条件更新和租约。重复消费不会重复投递已提交的 sent 记录；外部发送后、数据库写回前崩溃可能造成重投，这是 SMTP/Telegram 的至少一次交付边界。不能宣称外部通知严格恰好一次。

## 故障处理

1. 查看工单标题、节点/插件/实例、版本、首次失败时间、自愈动作、通知结果。
2. 连续失败至少 3 次且至少 2 分钟成立；凭据/权限/签名/配置错误直接转人工。重大为安全/完整性/Control 不可用及多节点阈值。
3. 技术员认领。30 分钟无人认领或从首次失败起 2 小时未恢复升级负责人。认领不重置首次失败时间。
4. 重大/升级且无人认领每 30 分钟提醒；认领后每 2 小时汇总。维护/停用排除使用 `PUT /api/v3/maintenance/nodes/:id/state` 的 `maintenance` / `disabled` 布尔值；该设置不修改系统网络或代理节点状态。
5. 持续健康 5 分钟恢复，停止升级、取消未发送故障通知并发恢复通知。填写处理记录后人工关闭；未关闭复发沿用原单，关闭后复发新建并关联原单。

多节点判定在相同环境按首次失败的 5 分钟窗口去重节点：至少 2 个且占符合纳管条件节点至少 20%，或至少 5 个；排除代理节点的禁用状态和明确运维排除标记。延迟上传仍保留原首次失败时间。

## 插件安装、升级与人工回滚

现有 `/admin/control` 管理签名发布、安装和配置。先注册受信签名、上传校验通过的包、建立节点插件分配；签名不通过不可安装。生产调度需部署方明确配置现有 `plugins.control_execution_enabled`、`plugins.dispatch_enabled` 等执行开关，排队不代表节点已执行。

运维工作台的“插件操作与审批”通过独立变更请求绑定节点、machine-telemetry 版本、操作、配置散列。单节点重启/恢复已验证版本可由技术员执行；新版本和批量变更必须负责人审核该请求的具体绑定。批准后变更不能修改，重复执行返回原操作链。检查 Agent 返回的最终状态，失败后保留审计，由人工判断下一次动作。

人工回滚前确认同节点该版本的执行与健康记录、已签名包、兼容配置和备份。选择回滚版本，创建并执行请求，观察健康恢复。Agent 自动修复只做允许的重试/实例重启，不自行升级或回滚配置。数据库、系统网络、证书信任等修改须负责人独立审批和维护窗口，不在本次新增执行器中。

## 通信、安全与保留

事件经现有已认证 `/api/v2/node/ws` 或 `/api/v2/agent/ws` 会话进入；节点 ID 来自认证结果，事件和外层冒充其他节点会拒绝。ForwardNode 与代理 Node 是独立资源，ForwardNode 不可借同数值 ID 上报代理节点运维事件。Agent 插件命令可以继续使用 gRPC，运维事件同时需要可达 HTTP(S) ApiHost 的 WebSocket。

协议 `anixops.maintenance/v1`；每批最多 50 条、256 KiB，单条最多 16 KiB。成功确认表示事件事务已持久化，工单消费可稍后完成；数据库失败不确认。event_id 数据库唯一，摘要指纹拒绝同 ID 不同内容。坏事件独立拒绝/退避，不中断兄弟事件。已消费 ID 在事件保留期内仍去重；长期离线的旧观测不能回退已记录的状态。

服务端丢弃客户端 `redacted_summary`、`diagnostic_ref`、`ticket_key` 自由文本，只展示结构化合法字段；“已脱敏”命名不是可信证明。详细诊断 30 天、事件与通知 90 天、关闭工单摘要和记录 1 年；未关闭工单证据不清理。变更审批审计保留至少 1 年；未结束变更保留。

## 上线前独立门槛

真实邮件和 Telegram 验证、独立监测 Control `/health`、真实跨地域网络/设备、灰度观察和交接均需实际证据。见 [外部监測评估](guide/maintenance-external-monitoring.md)。CI 不执行生产变更，也不发送真实通知。
